# KeepFit 进食记录升级研究方案

日期：2026-10-22。状态：研究与设计建议，尚未实现、尚未开展模型对比或称重验证。研究对象是以中餐、家庭共餐、食堂和外卖为主的日常记录用户；规划下一次核心体验升级，并把云识别与拍照分阶段推进。本轮只新增设计材料，不改动 App 行为或发布版本。

## 判断

把记录单位从“选一个食物并填克数”升级为“一餐里，我实际吃了哪些菜和多少”。用户提供自己知道的信息，产品保留不确定性；识别、份量估计、营养计算分别负责，降低输入负担，同时避免虚假精度。

## 现状证据与优先级

| 优先级 | 已观察问题 | 当前实现证据 | 产品动作 |
|---|---|---|---|
| P0 | 成品菜难找，食材分类与用户想法不一致 | FoodSelectionSheet 按 FoodCategory 分组；名称/别名包含检索，无独立成品菜/最近/常用入口 | 成品菜、基础食物、包装食品分开；默认展示最近与常用；整餐多选 |
| P0 | 份量问题被交回给用户 | FoodItem 已有 FoodPortion，但主录入仍用 g/ml，识别确认页只允许修改 grams | 以半碗、一碗、个数、小/中/大份、我的分食比例为主，克数作为可选高级输入 |
| P0 | 一份、一盘与实际食用份额混淆 | commonDishes 的“份”使用“盘”别名；FoodLog 没有整盘与个人份额字段 | 分开存菜品容器份量、实际吃下的比例；不能把四人聚餐自动当成每人四分之一 |
| P0 | 未知菜品会获得过于确定的营养数字 | ChineseDishNutritionEstimator 固定配比混合食材、按烹调词增加营养值，并给未知菜赋默认份重 | 未收录保留原菜名、候选和不确定项；估算依据清楚，必要时允许营养待完善 |
| P0 | 口语不能稳定理解 | FoodTextParser 是名称/别名、正则和关键词规则；没有大模型调用；代码没有独立 Speech/录音模块 | 保留离线确定规则，增加可替换的语义解析；语音转写和语义解析分别评测 |
| P1 | 原始份量和估算依据没有完整保留 | ParsedFoodEntry 的 quantityDescription、amountWasEstimated 等是草稿字段；FoodLog 保存 gram/per100g，未保留这些语义 | 新记录保留原话、原始单位、份额、来源版本与营养快照；历史记录不重算 |
| P1 | 图标追求逐菜精确，维护负担大 | IconCatalog 使用食物 ID/类别回退；复杂菜使用多个 emoji 组合 | 以菜品类别图标为主，菜名为准；用户照片可作缩略图，不要求每道菜专属图标 |

以上频率不能由源码推断。当前只有本次用户反馈与实现证据，没有 KeepFit 全量行为数据或用户访谈样本。

## 目标流程

1. 点“记一餐”，时间默认当前，可改早餐/午餐/晚餐/加餐。
2. 默认看到“最近吃过、我的常用餐、搜菜”。支持一次加入多道菜。
3. 可说一句话或粘贴文字，如“中午半碗米饭，番茄炒蛋吃了几口，红烧肉三块”。
4. 显示简短清单：菜名、实际吃下的量、需要确认的项目。任何候选都可换菜、改单量、删除或补充，只有最终确认才写入记录。
5. 已明确的数量直接保留；只有会显著影响结果的未知项才补问，目标每餐最多一到两个简短问题。仍不确定时可保存待完善记录，不能把未知食物当零热量。
6. 可保存为“我的常用餐”；下次复制并按本次吃下的份量调整。

## 份量设计

| 场景 | 用户看到的选项 | 关键约束 |
|---|---|---|
| 饭、粥、面 | 碗型 + 半碗/一碗/一碗半；少量/正常/较多 | 不同食物使用各自换算；同样碗型不代表相同克重 |
| 鸡蛋、包子、饺子、肉块 | 个数 + 必要时大小 | 不明确大小时标注估算，不要求用户称重 |
| 一人套餐、外卖 | 一份的 1/4、1/2、3/4、全部，必要时套餐小/中/大 | 盖饭中的饭与菜可拆开调整，但不能整份和拆分项重复计入 |
| 家庭/餐厅共餐 | 这盘菜的 1/4、1/3、1/2；或“我夹到自己碗里的小/中/大份” | 区分全桌与本人；聚餐人数只作辅助，不能默认平均分食 |
| 火锅、麻辣烫、自助 | 以实际选取的食物组为主，蘸料/主食/汤另列 | 不把笼统“一顿火锅”强行绑定一个固定重量和热量 |
| 带骨、带壳 | 按可食部分模板，必要时标注带骨/去骨 | 份量图谱注明原状、熟重、可食部，避免生熟与骨壳混淆 |
| 包装食品 | 标签每份/每100g + 实吃包数/比例 | 标签录入或扫描后仍允许核对单位、净重和食用比例 |
| 确实不知道 | 保留菜名/照片，待补充或主动采用明确标注的粗略模板 | 不删除记录，不用高精度数字掩盖未知，也不视为零摄入 |

份量参照图应来自已称重实拍或有相应使用权的数据集，带统一餐具/尺度和食物状态说明。AI 生成的食物图可用于气氛展示，不能充当计量标尺。可选“我的饭碗”一次设置，但不要求用户先称碗才能开始使用，也不使用统一密度将所有 ml 转成 g。

## 中餐菜品与营养来源

- 按菜品实体而不是纯食材列表组织：菜名、别名、菜系/类型、烹调方式、典型配方、常见成品份量、可食部、来源与版本。
- 先覆盖能验证的高频家常菜、食堂菜、面饭点心和套餐。首批可把 80–120 道作为规划范围，数量不是验收指标，不靠自动生成数千菜名扩库。
- 同一道菜允许家常/餐馆等配方候选；只在有数据支持时调整用油等参数。“少油”不能被当成已知油量，“餐馆版”也不能一律乘固定系数。
- 原材料数据、配方、烹调损耗、熟制产量与菜品份量分开。带有 USDA 引用的自建配方，必须清楚注明哪些值来自该数据库、哪些配比与用油是假设。
- 包装食品/连锁菜品以对应产品和有效标签为依据；不能用其他国家同名菜直接代表本地餐馆版本。
- 中国食物成分数据的商业授权需单独确认；当前代码只预留了授权数据导入入口，仓库没有发现该授权 JSON。USDA FoodData Central 的开放数据可作基础补充，但不能解决中餐配方差异。
- 展示“约 X kcal、按常见配方估算”，按误差尺度取整；只有完成样本验证后才展示有意义的参考范围。未经校准的范围不能标成统计置信区间，模型自报 confidence 也不是热量正确概率。
- 不因体重变化自动修改历史摄入记录；不把未记录清楚的摄入当成精确热量赤字。

## 文字与语音架构建议

输入 → 转写（仅语音需要）→ 结构化理解 → 菜品候选检索 → 份量与营养引擎 → 用户确认 → 保存。

1. 离线层：常用菜/别名、明确单位换算、模板、历史偏好；无网络仍能完成手动记录。
2. 语义层：模型提取时间、菜名、数量、共享语义、否定/改口、剩余、烹调描述和未知项。输出必须符合结构；不要让语言模型单独生成最终热量。
3. 语音层：在实际支持的系统/硬件/中文 locale 上测试 Apple SpeechTranscriber；不支持时保留系统听写或旧接口。用相同餐饮录音对照阿里云百炼支持热词/上下文增强的语音模型。模型及地域兼容性按上线当时文档核验，当前不宣布哪家准确率最好。
4. 词表：菜名、地方别名、品牌、单位与用户近期常吃菜。使用近期词表会降低整库热词偏置，不能为纠正一个词而把其他发音相近的菜强行改名。
5. 纠错：保留可编辑转写文本；“不是米线，是米粉”“没吃米饭”“还剩半碗”等需要保留动作/否定/剩余语义，不能只找食物关键词。
6. 修订反馈先作用于本用户，不将一个人的改菜/改量自动变成全库标准或训练数据。
7. 云调用由后端代理、控制额度与成本，Key 不进 App。用户明确启用云识别后只发送本次必要输入，不连带上传健康记录；音频默认不长期保留。此为设计建议，本轮未调用模型、未产生推理费用。

“换一个强模型”需要 A/B 评测，而不是凭通用排行榜选型。准备脱敏/授权的普通话、口音、中英品牌混说、餐厅噪声短录音，并把转写错与理解错分开报告。

## 图标策略

- 约 12–20 个菜品类别图标即可覆盖炒菜、炖煮、汤羹、面饭、点心、饮料等。明确菜名与适度颜色区分承担主要识别任务。
- 图标是浏览辅助；品类图标不参与判断食材、过敏原或营养。
- 自定义菜有统一回退图标，也可以使用本用户自摄照片。
- Thiings 仍遵循先前仅做方案的范围：未购买商业授权，不下载、内置或发布其素材。未来获得授权后按类别选图，无需逐菜追求完全对应。

## 实现与兼容

新条目建议保存：mealID、dishID/自定义菜名、输入原文、数量与单位、容器/份量模板版本、实际吃下的比例、可选估计熟重及范围、配方/数据源版本、估算标记、最终营养快照与人工修订。

保留现有 foodID 与历史营养快照；用向后兼容的可选字段/迁移补充信息。旧记录保持原有结果，不能因菜品库更新而漂移。草稿未确认不写入记录或 Apple 健康；重复识别或重试不能重复记一餐。

## 推进顺序

**第一阶段：可离线使用的记录升级，建议作为 1.2.0 的核心。** 先做一餐多菜、常用/最近、成品菜入口、家用份量/分食、可编辑确认、来源与估算保留、统一图标回退。无需新云后端，先让手动录入真正好用。

**第二阶段：文字与语音升级。** 先跑同一套测试语料比较现有规则、候选语义模型与语音引擎，再接入合适方案；保持离线入口。记录耗时、纠正次数、成本与失败回退，做出可用的半自动确认体验。

**第三阶段：拍照、标签扫描、菜单辅助。** 拍照先建议“可能有哪些菜”，由用户确认份量及本人食用比例；可选餐具参照/餐前餐后图。不要把一张聚餐照片解释成一个人的整餐，也不承诺单图准确测重或推断隐藏用油。

阶段按依赖和风险划分，没有估算开发工期或承诺上线日期；需要原型与样本评测后再拆分排期。

## 验收与评测

附 `evaluation-cases.json`：30 个设计测试场景，标注需要捕捉的语义与禁止行为。它是待执行的测试集种子，不是已通过的测试结果，也不包含营养真值。

- 对中文菜名/别名、明确份量、多人分食、否定改口、剩余、未知菜分别计分；按家庭/食堂/外卖、文字/语音划分，并保留未参与开发的测试集。
- 候选目标：高频范围内 Top-3 菜品命中至少 95%；明确份量语义正确至少 95%。均为提议门槛，尚无实测结果；不能用这两个数当作热量准确率。
- 严重错误：把没吃/别人的食物算成已吃、默认平均分、未知菜静默丢弃、重复计入、未经确认落库。固定回归集中应全部拦住。
- 用户任务目标：常用餐复记中位数约 5 秒以内；初次三道常见菜记录中位数约 20 秒以内；大多数明确输入无需补问，复杂输入尽量最多补问两次。它们是待验证目标，不能替代实际用户测试。
- 营养评测：用称重原料、实际用油、成品产量与可食部分制成参考餐，对总体与中餐各场景分别报告餐级能量误差中位数/P90、系统性偏差、估算范围覆盖与用户修订率。餐馆无法建立真值的餐食不能宣称测量准确率。
- 5–8 名真实目标用户的任务测试用于发现交互问题，不足以推断所有用户的需求频率。需要另行征得参与者对录音/照片使用的同意。

## 来源地图与证据边界

1. 本次用户反馈 + KeepFit 当前源码：最直接的产品问题证据，但没有全量使用数据。主要文件 Models.swift、FoodSelectionSheet.swift、EatWellView.swift、Utilities.swift/FoodTextParser、SeedData.swift、DataStore.swift、IconCatalog.swift。
2. [中国食物份量图谱验证研究，2021](https://onlinelibrary.wiley.com/doi/10.1111/jhn.12844)：50 名大学生、303 种食物的视觉参照研究，支持称重实拍图辅助份量判断；样本与使用方式不等于 KeepFit 上线效果。
3. [Apple SpeechTranscriber 文档](https://developer.apple.com/documentation/speech/speechtranscriber)：硬件与 locale 的可用性必须动态检查；不代表在中国菜名上的实测质量。
4. [Apple SpeechAnalyzer WWDC25](https://developer.apple.com/videos/play/wwdc2025/277/)：端侧转写技术路径与模块结构；不保证覆盖所有系统/设备。
5. [阿里云百炼语音准确率增强文档](https://help.aliyun.com/zh/model-studio/improve-asr-accuracy)：热词与上下文可用性、模型和地域限制；产品宣传不作为本 App 的准确率结论。
6. [USDA FoodData Central API 指南](https://fdc.nal.usda.gov/api-guide/)：公开数据与 CC0 条款，适合基础营养补充；不提供本地中餐餐馆配方真值。
7. [中国食物成分数据中心](https://fndc.chinanutri.cn/)：官方数据来源线索，访问需要登录；本次没有获得商业授权或批量数据。
8. [合餐用户的一手讨论](https://www.reddit.com/r/caloriecount/comments/17fxqko)：多人共菜与个人份量难记录的类似案例，只作补充定性信号，不使用网友给出的热量或饮食建议作为依据。
9. [餐馆中餐份量的一手提问](https://www.reddit.com/r/caloriecount/comments/1v8ez5x/how_many_calories_for_this_plate_of_chinese_food/)：近期的定性问题线索，不能代表普遍频率，评论中的营养数字未验证。

本次未访问私有客服、CRM 或用户行为数据，也未开展模型基准、真人访谈和称重实验。图片估量的几何限制是研究中的一般背景；实际产品的可靠性要用自己的样本验证。
